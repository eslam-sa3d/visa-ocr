visa-ocr @VERSION@ (build @TAG@) - deployment notes for the server team
======================================================================

WHAT THIS IS
  An OCR service for passports, visas and ID cards. The portal sends an image, gets a job id, and polls for the result.
  It runs fully offline. One container, one HTTPS port. No database is required (it keeps jobs in a small encrypted file
  on its data volume); PostgreSQL is optional for several servers sharing one queue.

BEFORE YOU START
  [ ] Linux server, Intel/AMD 64-bit, Docker with the compose plugin. The service sizes itself to its container:
      one reader for each CPU core, as long as each has about 2 GB RAM (6 cores and 18 GB -> 6 readers). Measured on a
      2-core test machine with generated documents: about 17 documents a minute for each core. GET /readyz shows the
      number of readers chosen.
  [ ] The server does NOT need internet access.
  [ ] Only the portal's servers should be able to reach this service. Do not expose it to the internet.
  [ ] A TLS certificate and key for the service's host name, from your organisation's CA.

1. VERIFY AND LOAD
     sha256sum -c SHA256SUMS.txt
     gunzip -c visa-ocr-@TAG@-amd64.tar.gz | docker load

2. MAKE THE KEYS  (once; as root)
     docker run --rm --entrypoint id visa-ocr:@TAG@          -> note the uid of the service user
     python3 production/make_keys.py /etc/visa-ocr --owner <that uid>
   This writes /etc/visa-ocr/keys.json (digests only) and /etc/visa-ocr/data.key, and PRINTS three API keys once:
     portal  (uploader)  upload documents, read its own results      -> give to the portal team
     review  (reviewer)  read any result, submit corrections
     ops     (admin)     list models
   Store the keys and data.key in your key management system. Keys expire after a year (--expires YYYY-MM-DD to change);
   to rotate, add the new entry to keys.json before removing the old one.

3. ADD THE CERTIFICATE AND THE LOG FOLDER
     mkdir -p /etc/visa-ocr/tls /var/log/visa-ocr
     cp <your certificate> /etc/visa-ocr/tls/server.crt ; cp <your key> /etc/visa-ocr/tls/server.key
     chown -R <that uid> /etc/visa-ocr /var/log/visa-ocr ; chmod -R go-rwx /etc/visa-ocr

4. REVIEW THE SETTINGS AND START
     Open production/visa-ocr.env. Three lines are marked DECIDE (time limit, parallel jobs, malware scanner); the rest is
     ready. Then, from the production folder:
       IMAGE_TAG=@TAG@ docker compose up -d
   If it does not start:  docker compose logs
   In production mode it refuses to start when something is unsafe (no key file, no certificate, storage not encrypted)
   and prints exactly what.

   Without compose, the same thing as one command:
     docker run -d --name visa-ocr --restart unless-stopped -p 443:443 --read-only --tmpfs /tmp --cap-drop ALL \
       --security-opt no-new-privileges --env-file production/visa-ocr.env \
       -v visa-ocr-data:/data -v /etc/visa-ocr:/etc/visa-ocr:ro -v /var/log/visa-ocr:/var/log/visa-ocr visa-ocr:@TAG@

5. CHECK IT WORKS
     curl --cacert <your CA> https://<host>/healthz                         -> {"status":"ok"}
     curl --cacert <your CA> https://<host>/readyz                          -> {"status":"ready","authEnabled":true}
     curl --cacert <your CA> -H "X-API-Key: <ops key>" https://<host>/v1/models   -> the models, each "verified"
   Upload a test image with the portal key and poll the job:
     curl --cacert <your CA> -H "X-API-Key: <portal key>" -F "files=@passport.jpg" https://<host>/v1/documents/extract
     curl --cacert <your CA> -H "X-API-Key: <portal key>" https://<host>/v1/jobs/<jobId>
   The full system test is in tools.tar.gz. It draws its own test documents and sends nothing real. It needs a key that
   may do everything, so run it on the TEST environment with a temporary "full" key in keys.json, from a workstation with
   Python 3.12, the packages in requirements-lite.txt and "requests":
     tar -xzf tools.tar.gz && python tools/system_test.py --url https://<host> --key <full key> --key2 <second full key>

6. MEASURE  (before go-live; results go into GO_LIVE_RECORD.md)
     python tools/perf_test.py --url https://<host> --key <portal key> --phase load --levels 1,2,4,8 --n 40
   Size the number of containers and JOB_THREADS from the result, and set OCR_DEADLINE_SECONDS from the read times you
   see with your own sample images. Every timing known so far is from a laptop.

7. OPERATE
   Logs      docker logs visa-ocr            application log; holds no document data
             /var/log/visa-ocr/audit.log     security events, one JSON line each: send to your SIEM
   Health    /healthz for liveness, /readyz for readiness (both need no key)
   Data      Results are deleted after 60 minutes and are encrypted while stored.
   Training  Collection is ON: for uploads the portal sends with consent_training=true, the images and the reviewers'
             corrections are kept encrypted under /data/training for 30 days (TRAINING_RETENTION_DAYS). Uploads without
             consent are never kept. To switch it off, remove TRAINING_STORE_DIR from production/visa-ocr.env.
             A correction counts only after a second person approves it. Retraining runs on a separate training machine
             and a new model is activated only if it beats the current one on the golden set: docs/MODEL_TRAINING.md.
   Backup    Back up nothing from the data volume except /data/training if you want to keep corrections beyond a server
             loss. Keep /etc/visa-ocr in your secret store.
   Update    Load the new image, set the new IMAGE_TAG, `docker compose up -d`. To go back, use the old tag.
   Scale     Give the container more cores and memory: it starts more readers by itself at the next start. Beyond one
             server, run more containers behind your load balancer and set DATABASE_URL to a PostgreSQL database, so they
             share one queue (tested: an upload sent to one container is read and answered through another).

FOR THE PORTAL TEAM
  When the applicant should take the photo again, the response carries a "retake" block. Show retake.message to the
  applicant. It appears in three places:
    - on the upload call itself: HTTP 422 with detail.code image_unclear and detail.retake, when the photo is plainly
      unusable (blurred, dark, washed out, too small). Answered at once, whatever the load; no job is created.
    - in error.retake when the job failed (codes image_unclear, mrz_not_found and multiple_documents).
    - in result.retake when a document was read but a check digit fails, or when a passport's page is cut off in the
      photo (flag page_cut_off: the reading is returned, a person reviews it, the applicant is asked for the whole page).
  A reading whose check digits all pass carries it only when the passport page is cut off.
  POST /v1/documents/check answers at once whether a photo is clear enough, before it is sent for reading.
  POST /v1/passports/extract is the passport-only endpoint: same upload and same result as /v1/documents/extract, but
  only the MRZ of a passport is accepted (anything else fails with not_a_passport or mrz_not_found and a retake message).
  POST /v1/photos/check checks the applicant's personal photo at once: one face, large enough, centred, sharp, well lit,
  on a light plain background. Refuse the photo when "acceptable" is false and show retake.message.
  Send the applicant's form data with each upload: it confirms the name and nationality, which no check digit covers.
  Examples: docs/API_EXAMPLES.md in docs.tar.gz.

OPEN BEFORE GO-LIVE (tell your security and business owners; details and owners in GO_LIVE_RECORD.md)
  - Accuracy has not been confirmed by a person against real documents.
  - No load or timing figures from production hardware.
  - No independent penetration test or second-person source code review.
  - Not a statement of compliance with NCA controls; docs/NCA_CONTROLS.md lists what the service does and what must be
    supplied around it.
  - The front of European, UK and US residence cards and Omani cards is read from printed text with nothing to confirm
    it: every such reading goes to review. It was built against about 85 sample images and its values have not been
    checked by a person. Ask applicants for the MRZ side when the card has one.
